# From Primitive Provenance to Mathematical Structure

**Lean-community review snapshot - 9 August 2026**

This directory is a review-oriented, unpacked snapshot of the CNNA project at the current formal frontier. It is **not** presented as a completed physical theory and it does not claim that later target structures must emerge. The immediate question is narrower:

> Given deliberately minimal provenance data, what mathematical structure can actually be derived without assuming the intended output in the input?

A methodological rule drives the project:

> **Do not assume as input what the construction is meant to derive as output.**

This rule is the reason the project keeps a deliberately small, mathlib-free Lean Core and places stronger mathematical verification in a separate proof package.

The allowed dependency direction is intentionally one-way:

```text
CNNAProofs  --->  CNNA Core
                 ^
                 |
             no mathlib
```

The Core contains domain definitions, the constructive derivation and elementary closure lemmas that can be expressed with Lean/Core alone. Mathlib is allowed only in the separate proof layer. This is a design choice for review, not a claim that mathlib is undesirable.

## What is worth reviewing now?

The project is being shown **before** the later F1/F2 skew-symmetric structure is formally reached. That is intentional: architectural criticism is more useful before more nodes depend on the current interfaces.

In particular, feedback is requested on:

1. whether the Lean modeling is correct and reasonably idiomatic;
2. whether the Core / proof-package boundary is sensible;
3. whether any desired result is already hidden in a type, constructor, imported abstraction or interface assumption;
4. whether the theorem boundaries are strong enough to be nontrivial rather than merely restating definitions;
5. whether the Python finite evidence and Lean universal claims are kept epistemically distinct;
6. whether the DAG and documentation make dependencies and proof ownership understandable;
7. whether the repository organization is reviewable without relying on an LLM;
8. where standard Lean/mathlib abstractions should replace local infrastructure without violating the provenance discipline.

See [community/COMMUNITY_OVERVIEW.md](community/COMMUNITY_OVERVIEW.md) or the rendered [community/COMMUNITY_OVERVIEW.pdf](community/COMMUNITY_OVERVIEW.pdf) for the short review note, and [community/COMMUNITY_THREAD_DRAFT.md](community/COMMUNITY_THREAD_DRAFT.md) for a proposed Lean-community introduction.

## Four complementary representations

The project is not maintained as Lean code alone:

- **Lean** certifies deduction for the claims that have been formalized.
- **Python** explores finite instances, searches for counterexamples and provides regression evidence.
- **Documentation** states intended semantics, proof obligations and interpretation boundaries.
- **DAG / registry** records provenance, dependencies, proof ownership, finished/open status and the current frontier.

No one representation is treated as sufficient by itself.

## AI-assisted workflow

AI use is explicit. ChatGPT has been used for broad structural search, hypothesis and proof construction, integration and code work; Claude has been used as an additional coherence/review partner. LLM output is **not** treated as proof evidence merely because it was generated by an LLM. Lean kernel checks, executable tests, source hashes and review boundaries remain distinct evidence layers.

The repository is also intentionally machine-readable: the snapshot can be downloaded and supplied to a capable LLM so that code, DAG, documentation, hashes and open obligations can be explored together. This is an accessibility feature, not a substitute for human-readable documentation or kernel verification.

See [community/AI_AND_RESEARCH_WORKFLOW.md](community/AI_AND_RESEARCH_WORKFLOW.md).
